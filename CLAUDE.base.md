# CLAUDE.base.md

Базовые универсальные инструкции для AI агента.

## Языковые настройки
- **Язык кода:** английский
- **Язык общения:** русский
- **Форма обращения:** на «ты»

## Общие правила кода
- **Принцип:** код должен быть самокомментированным для любого языка
- **Эмодзи:** не использовать ни в коде, ни в комментарияx
- **Актуальность версий:** всегда проверять актуальность кода в открытых источниках используемых библиотек и фреймворков, использовать только актуальные версии, избегать устаревших методов и функций

## Поведение агента после реализации
- Не нужно досконально проверять решение после его реализации, если не указано иное явно
- Не нужно проверять, применились ли внесённые изменения

## Архитектурные принципы разработки ПО

При проектировании и написании любого сервиса/скрипта исходить из трёх базовых допущений, если явно не указано иное.

### 1. Любая операция может завершиться ошибкой
- Сеть, диск, БД, внешний API, парсинг входных данных — всё это может отказать в любой момент, это норма, а не исключительный случай
- Разделять восстановимые ошибки (retry с backoff, fallback) и невосстановимые (fail-fast с понятным логом/исключением)
- Не глотать исключения молча (`except: pass` и аналоги) — логировать или пробрасывать
- Таймауты — обязательны для любого сетевого/IO вызова, который потенциально может зависнуть
- Операции проектировать идемпотентными: повтор после сбоя не должен приводить к дублированию данных или повторным побочным эффектам

### 2. Расчёт на горизонтальное масштабирование (несколько копий)
- Сервис/скрипт почти всегда должен уметь работать в нескольких одновременно запущенных экземплярах (несколько подов/процессов/воркеров)
- Не полагаться на in-memory состояние как на единственный источник правды (как кэш — можно, как единственное хранилище — нет)
- Разделяемые ресурсы (очереди, записи в БД, файлы) защищать через distributed lock / `SELECT ... FOR UPDATE` / атомарные операции, а не через process-local mutex
- Избегать гонок при конкурентной обработке одного и того же события/задачи несколькими экземплярами (дедупликация, идемпотентные ключи, `SET NX`)
- Состояние и конфигурация, которые должны быть общими для всех копий, живут снаружи процесса (БД, Redis, env), а не в локальных файлах конкретного инстанса

### 3. Расчёт на бесконечный поток данных и бесконечное время работы
- Процесс рассчитан на непрерывную работу (дни/недели/месяцы) и неограниченный поток входных данных, а не на разовый запуск с конечным набором данных
- Не накапливать в памяти неограниченно растущие структуры (списки/кэши/очереди без ограничения размера или TTL)
- Логи — с ротацией, файлы/директории с накапливаемыми данными — с ретеншеном/очисткой
- Graceful shutdown: обработка сигналов (SIGTERM/SIGINT), корректное закрытие соединений и завершение текущей единицы работы перед выходом
- Устойчивость к разрывам соединений с внешними системами (БД, MQTT, Kafka, RabbitMQ и т.п.) — переподключение с backoff, а не падение процесса
- Падение и перезапуск процесса не должны приводить к потере или дублированию данных (checkpoint/offset/resume — там, где это применимо)

### 4. Максимальная утилизация железа (GPU/CPU)
- Железо (GPU и CPU) должно использоваться по максимуму — если есть возможность загрузить CPU на 100% (многопоточность/многопроцессность), делать это
- IO-bound работу (сеть, диск, ожидание внешних сервисов) распараллеливать через многопоточность/async, CPU-bound — через многопроцессность или батчинг на GPU, не оставлять ядра простаивать
- GPU-инференс — батчить запросы там, где это возможно, вместо обработки по одному объекту за раз
- Не проектировать пайплайны с искусственно последовательным выполнением независимых по данным операций — распараллеливать всё, что не имеет зависимостей по данным
- При выборе между простотой однопоточного кода и утилизацией всех ядер — по умолчанию выбирать утилизацию, если задача это оправдывает по объёму данных

## Среда разработки

### Основные параметры
- **IDE:** JetBrains IDEA
- **Shell:** PowerShell (Windows) - команды для run_in_terminal должны быть PowerShell-совместимыми. ОСЬ - Windows.
- для новых терминалов, используемых агентом нужно вызывать команду
   ```chcp 65001 ; $env:PYTHONIOENCODING = 'utf-8' ;  .\.venv\Scripts\activate.ps1``` - только один раз на терминал, не каждый раз перед командой
- после этого один раз активировать виртуальное окружение из каталога проекта скриптом по полному пути:
   ```GIT_IDE_PROJECT_ROOT\.venv\Scripts\Activate.ps1 2>&1```

### PowerShell команды (важно!)
При использовании `run_in_terminal` tool:
- Разделитель команд: `;` (НЕ `&&`)
- Чтение файлов: `type` (НЕ `cat`)
- Использовать только PowerShell-совместимые команды
- Команды 'head' и 'tail' НЕ использовать, вместо них использовать:
  - `Get-Content -TotalCount n` для чтения первых n строк файла
  - `Get-Content -Tail n` для чтения последних n строк

**Пример:**
```powershell
cd path; python script.py    # Правильно
cd path && python script.py  # ОШИБКА в PowerShell
```

## Git-коммиты
- **Co-Authored-By** не упоминать в тексте коммита (ни `Claude`, ни другие соавторы-агенты)
- Текст коммита может быть на русском языке
- Коммит делать можно (после явного запроса "закоммить"), но **push** и **деплой в докер** (rebuild/redeploy образов) — только по отдельной явной команде, коммит сам по себе их не подразумевает

## Работа с файлами

### Создание файлов
- **НЕ создавать** тестовые скрипты/данные без явного запроса
- **НЕ создавать** `*.md` файлы без явного запроса
- **НЕ дублировать** существующие файлы проекта
- При создании файлов учитывать структуру проекта в IDEA

### Тестовые скрипты
- **НЕ генерировать** `test_*.py` без явного запроса
- **НЕ генерировать** `usage_example_*.py` без явного запроса
- Генерировать тестовые скрипты ТОЛЬКО если пользователь явно запросил

### Именование .md файлов

- `README.md` и `CLAUDE.md` — всегда остаются на своём месте, не переименовывать и не перемещать.
- Все прочие `.md`-файлы в директории:
  - либо начинаются с `_` в имени (чтобы отображаться первыми в листинге), например `_quickstart.md`;
  - либо называются строго по имени скрипта/инструмента, который они документируют, например `kb_tools_mcp_http.md` для `kb_tools_mcp_http.py`.

### Документация и отчеты
- если генеришь `SUMMARY_*.md`, `COMPLETE_*.md` и прочие файлы отчетов -- класть их в папку doc в рабочем каталоге
- если генеришь тесты, класть их в папку test в рабочем каталоге, вызывать из рабочего каталога
- **ОБЯЗАТЕЛЬНО обновлять** `README.md` в рабочем каталоге по мере выполнения работы
  - Добавлять описание новых функций/модулей
  - Обновлять инструкции по использованию
  - Документировать важные изменения
  - Актуализировать примеры кода
- Генерировать документацию ТОЛЬКО если пользователь явно попросил

#### Если отчет запрошен явно:
1. **Папка:** `.ai/`
2. **Формат имени:** `YYYYMMDD.NNN_<название>.md`
   - `YYYYMMDD` - текущая дата
   - `NNN` - порядковый номер (трехзначный, с ведущими нулями)
3. **Порядковый номер:**
   - Читается из файла `.ai/version.txt`
   - Инкрементируется при создании нового отчета
   - Сохраняется обратно в `.ai/version.txt`

**Пример:**
```
.ai/20260215.001_api_integration_report.md
.ai/20260215.002_database_migration_report.md
.ai/version.txt  # содержит: 002
```
