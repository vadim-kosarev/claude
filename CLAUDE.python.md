# CLAUDE.python.md

Короткие инструкции для ИИ при генерации Python-скриптов.

## Общие правила
- Эмодзи (emodji): не использовать. Пиши только текст
- Все файлы сохраняй в кодировке UTF-8, все нужные директивы в файле должны быть.
- Методы и функции должны быть максимально типизированны (использовать type hints и Pydantic)
- По возможности добавлять к методам тип возвращаемого значения
- Придерживаться принципов чистого кода (Clean Code) и SOLID
- Рекомендация, не требование: где уместно — использовать ООП и современные шаблоны проектирования (design patterns); не применять их насильно там, где проще и понятнее свободная функция
- Избегать избыточной сложности и дублирования кода (DRY)
- Использовать асинхронное программирование там, где это уместно
- Если не указано иное, использовать асинхронные методы и функции (async/await) для операций ввода-вывода и сетевых запросов
- Обновлять документацию метода/класса/модуля (docstrings) при изменении кода
- Не генерировать usage_example_*.py, test_*.py без явного указания
- Многострочные строки: использовать тройные кавычки (""" или '''), НЕ конкатенировать через "+" и "\n"

## Зависимости
- requirements.txt: Внешние библиотеки фиксируй в `requirement.txt`.
- Установка должна работать через: `pip install -r requirement.txt`.

## Переменные окружения и конфигурация
- .env файл: Храни переменные окружения в файле `.env` в папке запуска проекта.
- python-dotenv: Используй `python-dotenv` для загрузки переменных из `.env` файла (`pip install python-dotenv`).
- Конфиг-переменные: Все настраиваемые параметры, которые появляются в коде, вынеси в `.env`.
- Примеры переменных: `API_KEY`, `DATABASE_URL`, `DEBUG`, `LOG_LEVEL`, `TIMEOUT`, и т.д.
- Загрузка: В начале скрипта: `from dotenv import load_dotenv; load_dotenv()`
- .gitignore: .env файл должен быть в `.gitignore` (не коммитить в репозиторий).
- Приоритет конфигурации (от низшего к высшему): переменные окружения → `.env` файл (перезаписывает только незаданные через `load_dotenv(override=False)`) → аргументы командной строки. CLI-аргументы всегда побеждают.
- Именование в `.env`: `<script_name>.config.<cli-flag-name>`. CLI флаг `--frame-step` в скрипте `face_finder.py` → переменная `face_finder.config.frame-step`. Это даёт однозначное соответствие без таблиц маппинга.
- `.env.example`: рядом с `.env` держать `.env.example` с комментариями к каждому параметру. `.env` — только значения без комментариев.
- Относительные пути в `.env` резолвить от директории скрипта (`os.path.dirname(os.path.abspath(__file__))`), не от CWD.

## Логирование
- Используй стандартный модуль `logging`.
- Логи складывай в папку `logs/`.
- Если папки `logs/` нет, создавай её.
- Имя лог-файла — по имени запущенного скрипта с расширением `.log`: `logs/<script_name>.log`.
  Пример: скрипт `join_video.py` → лог `logs/join_video.log`.
  Получать имя через `Path(__file__).stem`.
- Уровень логирования читать из переменной окружения `LOG_LEVEL` (default: `INFO`).
  Пример: `getattr(logging, os.getenv("LOG_LEVEL", "INFO").upper(), logging.INFO)`.
- По возможности логируй и в файл, и в консоль.
- Используй ротацию логов - последние 7 дней максимум, 5 мегабайт на файл ограничение по объему
- **НЕ использовать** `print()` для вывода информации
- **Использовать** `logger.info()` и `logger.debug()`

## Структуры данных
- **НЕ использовать** `dict` для сложных структур данных
- Pydantic: **Использовать** Pydantic `BaseModel` для всех структур данных

## Запуск и интерфейс
- Каждый скрипт должен корректно запускаться без аргументов
- использует argparse
- При запуске без аргументов скрипт печатает справку (help/usage) и завершает работу без ошибки.
- Глобальный флаг `--debug` (перед субкомандой) для включения DEBUG-уровня логирования: `python script.py --debug process ...`
- Глобальный флаг `--env <path>` для переопределения пути к `.env` файлу (по умолчанию — `.env` рядом со скриптом)

### Порядок загрузки: CLI до тяжёлых импортов
Парсинг аргументов делать **до** загрузки тяжёлых зависимостей (сетевые клиенты, LLM, БД, ML-библиотеки).
Паттерн — два блока `if __name__ == "__main__"` в файле:
```python
# 1. Только stdlib — вверху файла
import argparse
import sys

def _build_parser() -> argparse.ArgumentParser: ...

# Ранний выход: --help или нет команды — до загрузки чего-либо тяжёлого
if __name__ == "__main__":
    _parser = _build_parser()
    _args = _parser.parse_args()
    if not getattr(_args, "command", None):
        _parser.print_help()
        sys.exit(0)

# 2. Тяжёлые импорты — только сюда доходим, если команда задана
import heavy_lib  # LLM, БД, fastmcp, и т.д.

# ... вся логика модуля ...

# Точка входа — использует _args из первого блока
if __name__ == "__main__":
    if _args.command == "run":
        ...
```

- типичные примеры запуска
```bash
# Показывает HELP
python my_script.py 
python my_script.py --help
python my_script.py help

# Выводит список команд, если скрипт с командами.
python my_script list

# Выводит help по команде
python my_script help <command>

# Вызывает команду
python my_script <command> [args...]
```

## Состояние
- tinydb: Если скрипту нужно сохранять состояние между запусками, используй `tinydb`.
- state/: Храни состояние в отдельном файле (например, в папке `state/` или рядом со скриптом).

## Тестирование
- pytest: Используй `pytest` для управления тестами.
- Установка: `pip install pytest pytest-cov pytest-xdist`
- Структура: Храни тесты в папке `tests/` в корне проекта.
- Запуск: `pytest` (все тесты) или `pytest tests/test_module.py` (конкретный файл)
- Конкретный тест: `pytest tests/test_module.py::test_function`
- С покрытием: `pytest --cov=src` (показывает процент покрытия кода)
- Параллельно: `pytest -n auto` (ускоряет тесты на многоядерных системах)
